# Читаемость, ответственность и конфиги

Применять при изменении/ревью C#. Это соглашения Emergency Shift, не требование переписать весь проект при любой задаче. Поведение, порядок событий и сериализованные значения сохраняются при рефакторинге.

Архитектурный приоритет — [SOD](../../sod-unity-architecture/SKILL.md). Ниже остаются совместимые правила читаемости и сохранности контента; прежние ограничения против DI и лимитов зависимостей удалены.

## Условия и форма записи

| Ситуация | Предпочтение |
|---|---|
| Недопустимый вызов, мёртвая цель, отсутствующая зависимость | Понятная guard-проверка с ранним выходом |
| Независимые события одного шага | Отдельные if: несколько из них могут сработать одновременно |
| Конечный набор состояний одного brain | Явный switch с названными обработчиками; State-объекты только при реальном усложнении |
| Выбор одной записи по ID/типу поверхности | Данные/lookup с явной обработкой отсутствующей записи |
| Разные алгоритмы оружия/вида врага | Контракт и отдельные реализации в точке вариативности |
| Отличаются только HP/скорость/угол/спрайты | Definition/profile/prefab, без нового класса поведения |
| Растущие else-if по виду врага в пуле, аудио и UI | Убрать знание вида из общих потребителей; определить контракт/данные |

Не заменять упорядоченную цепочку else-if независимыми if механически: это меняет число выполняемых действий. При переносе проверить приоритет и взаимоисключение ветвей. Сложный switch, который одновременно выбирает поведение, рисует UI и создаёт VFX, тоже требует разделения ответственности.

- Одно самостоятельное действие на строке; поля с разным смыслом объявлять отдельно. Пустые строки разделяют этапы метода.
- Четыре пробела, блоковые фигурные скобки, пробелы вокруг операторов. Для if/циклов использовать скобки даже при одном действии. Правила IDE находятся в корневом .editorconfig.
- Не вкладывать тернарные выражения. Простой выбор двух значений допустим; цепочка этапов уровня должна читаться как этапы.
- Выражения с несколькими проверками разбивать по смыслу, а не прятать произвольные куски в Helpers. Имя вроде CanBeginAttack должно описывать целостное правило; проверка не должна незаметно наносить урон.
- Не экономить строки за счёт `a=...;b=...;if(...){...}`. Короткое свойство чтения может оставаться expression-bodied.
- По SOD ориентир файла — 200–300 строк; превышение требует оценки связного разбиения, без массовой перестройки. Лимиты зависимостей — в SOD skill. Количество if само по себе не заменяет анализ ответственности.

## Границы класса

Перед добавлением ответственности назвать её владельца и причину изменения. Правила укуса меняются отдельно от отображения пасти; сохранение сцены отдельно от подсказки UI. Brain выбирает действие, общие компоненты исполняют механику, представление реагирует.

Маленькие интерфейсы, композиция и отдельные стратегии следуют SOD. Model не зависит от View, ввода или камеры; Unity-мотор и физика — отдельный адаптер. Возможный следующий вид не должен наследовать запрещённую для него реакцию Сталкера. Не прятать зависимости в универсальный Manager/Utils или context bag ради формального лимита.

Целевая композиция — Zenject/Extenject, constructor injection и installer фичи. Старые prefab/scene/Configure-связки сохраняются до явной миграции; не считать их новым архитектурным стандартом. В горячем цикле не искать всю сцену. Не добавлять скрытого глобального игрока. Для подписки, корутины, реестра и арендованного объекта обозначить срок жизни и прекращение работы.

## Что выносить в настройки

| Данные | Место |
|---|---|
| Баланс вида/оружия, реакция на свет, VFX/звук, повторяемые encounter-параметры | Тематический definition/profile; один источник истины |
| Конкретная позиция, маршрут, ссылки на дверь/предметы, область обнаружения | Экземпляр в сцене либо намеренно оформленный spawn override |
| Текущее HP, агрессия, патроны, активная волна, таймеры | Runtime-состояние экземпляра/сессии |
| Неизменная формула, нейтральное значение, технический идентификатор | Именованная const/static readonly там, где требуется смысл; не отдельный asset ради 0/1/Mathf.PI |

Скорости, длительности, число фрагментов/варианты, интенсивности и радиусы, которые нужно настраивать дизайнеру, не зашивать в алгоритм. Технические бюджеты можно оставить именованными константами до необходимости настройки; при настройке по устройствам/сценариям нужен отдельный профиль нагрузки.

Не вводить единый гигантский GameConfig. Не смешивать дефолт в коде, legacy-поля и SO без явной политики выбора. Runtime не пишет обратно в общий asset. Валидация проверяет диапазоны, единицы, обязательные ссылки и отношения значений, например начало выпада ≤ момент укуса ≤ конец допустимого окна. Inspector-атрибут не заменяет проверку некорректно загруженных данных.

## Проверка удобства расширения

Для выбранного изменения кратко пройти подходящий сценарий:

- Новая числовая разновидность врага: создать/назначить профиль, не менять пулю/камеру/HUD.
- Новый алгоритм врага: свой brain и видовые адаптеры, общие здоровье/движение/урон остаются.
- Новый уровень: сцена и описание целей, без копирования класса первого уровня.
- Новый материал попадания: запись набора/контракт поверхности, без списка видов врагов в оружии.

Показать, какие файлы действительно меняются и почему. Это мысленная проверка границ, не требование создать фиктивный контент или тест, проверяющий наличие интерфейса. Поведенческие тесты должны ловить приоритет ветвей, двойной урон/смерть и утечку состояния между экземплярами.
