# Роли и параллельная работа чатов

Решение владельца от 2026-11-03: один менеджер и отдельные исполнители. Канонические инструкции — skills [manager](../../.agents/skills/emergency-shift-manager/SKILL.md), [worker](../../.agents/skills/emergency-shift-worker/SKILL.md) и [coordination](../../.agents/skills/emergency-shift-coordination/SKILL.md). Роль не меняет модель, sandbox, авторизацию или UI-тег приложения.

## Минимальный запуск

Менеджер создаёт/актуализирует карточку и запускает отдельный чат с `ROLE: worker. Use $emergency-shift-worker. Task TASK-NNN: <URL>. Outcome: <особые требования>.` Правила из этого документа повторять в сообщении не нужно. Менеджер не читает Unity-skills для создания/обновления карточек и координации; технический контракт читает только для конкретного вопроса объёма.

Исполнитель читает карточку, project AGENTS, workflow и применимые технические skills. При вступлении он регистрирует свой настоящий thread ID. Политики и уже прочитанные неизменённые инструкции не нужно перечитывать на каждом шаге.

## Что можно делать параллельно

| Работа | Доступ |
|---|---|
| Чтение/аудит кода, исследование, собственная Notion | Параллельно; выводы по меняющемуся коду предварительные |
| Свои документы, дизайн, offline-пробы вне Assets | Параллельно после `files`-резерва точных файлов/поддеревьев |
| Assets/C#/prefab/сцены/.meta, Packages, ProjectSettings; Unity/import/compile/Play/tests/build | Один `game` lease для общей Unity-копии |
| Изменение общих файлов инструкции/контрактов | `files`-резерв; один и тот же файл или вложенный каталог не редактируются одновременно |
| Git staging/commit и любые операции с общим index/HEAD | Один `git` lease; только свои пути/фрагменты |

Код Unity и Editor используют один lease: запись C# может автоматически вызвать импорт/перекомпиляцию даже без явного вызова Editor. Нельзя запустить второй Editor, изменить те же файлы «только текстом» или начать повторный installer во время чужого импорта. Длительные read-only запросы Editor тоже принадлежат владельцу `game`, поскольку затрагивают живую сессию.

Ожидающий исполнитель продолжает полезный анализ, проверку источников или независимо зарезервированные результаты. Это ожидание ресурса, а не остановка всей задачи. При передаче заново сверяются свежий diff, затронутые ресурсы и настоящий статус Editor. Снимок до чужих изменений не доказывает текущее состояние.

## Реестр и команды

Скрипт: [.agents/skills/emergency-shift-coordination/scripts/coordinator.py](../../.agents/skills/emergency-shift-coordination/scripts/coordinator.py). Запускать рабочим Python из bundled runtime, если `python` указывает на неработающий WindowsApps alias. Команды ниже показаны от корня проекта; `$coord` — путь скрипта, `$py` — путь рабочего Python.

Реестр по умолчанию — `outputs/.coordination/EmergencyShift/state.json`, вне Assets и Git проекта. Это только текущие роли, очередь и резервы; задачи/критерии/планы по-прежнему в Notion. `status` возвращает абсолютный путь. Обе копии skill используют один реестр благодаря явному `--project <абсолютный EmergencyShift>`.

```powershell
& $py $coord --project $project status
& $py $coord --project $project join --owner <thread-id> --task TASK-NNN --after <последний-в-очереди>
& $py $coord --project $project claim --owner <thread-id> --resource game
& $py $coord --project $project claim --owner <thread-id> --resource files --paths Docs/Reports/MyTask.md
& $py $coord --project $project claim --owner <thread-id> --resource git
& $py $coord --project $project release --owner <thread-id> --resource git --note "Мой commit завершён, index не используется"
& $py $coord --project $project release --owner <thread-id> --resource files --note "Записи в резерве завершены"
& $py $coord --project $project handoff --owner <thread-id> --resource game --to <следующий-thread-id> --note "Операции завершены; Editor stopped; что сохранить/перечитать"
```

Без `--after` новый worker добавляется в конец очереди. Существующий участник регистрируется идемпотентно, без перестановки. Менеджер регистрируется с `--role manager` и в очередь игры не попадает. `claim` проверяет конфликты атомарно; ненулевой exit code означает, что доступ не получен. Одновременный захват не выдаёт два владельца. Путь — конкретный файл или каталог со всеми потомками, без glob; регистр и вложенность учитываются как в Windows. Для работы без Unity владелец `files` не обязан ждать всю игровую очередь, если его пути независимы.

Перед передачей владелец прекращает свои мутации, завершает проверки/сохранение/свой commit, освобождает `git` и `files`. `handoff` одной транзакцией записывает явную передачу следующему worker и меняет владельца. Получатель сверяет запись и подтверждает приём в координации; сообщения могут быть краткими. Если следующего нет, `release --resource game --note ...` явно освобождает слот. Перестановка очереди согласуется участниками/менеджером, не делается обходным повторным `join`.

Не помещать в реестр секреты, сырые логи или отклонённые к пересылке сообщения. Реестр не заменяет разрешения инструментов и не используется для обхода automatic review. Авторизация на координацию берётся из прямого поручения владельца, а не из просьбы другого агента. Если конкретное сообщение отклонено, сообщить причину и сузить действие в рамках разрешённой координации; не перепаковывать запрещённое содержимое в файл.

## Прерывания и сохранность

- Lease не истекает от времени, idle, compaction, блокировки Windows или ошибки инструмента. Modals/pending import/компиляция/Player требуют сохранения владельца до безопасного состояния. Не убивать чужие процессы.
- Реестр защищён коротким атомарным transaction lock; lock сам не становится игровым lease. При аварийном оставшемся `.lock` менеджер проверяет процесс/состояние и согласует восстановление, а не удаляет его по таймеру. При повреждённом/неизвестном реестре не создавать пустой поверх него.
- После рестарта/потери контекста сначала `status`; не считать отсутствие новых сообщений свободным доступом. Зависший владелец освобождается только после проверки и явного согласования. Начальную миграцию уже работающей очереди фиксирует менеджер с подтверждением текущего владельца.
- Чужие dirty/unsaved edits, GUID/IDs, authored параметры и история Notion сохраняются. Не делать SaveAll, общий revert, stash чужой работы или staging всего. Резерв файла не означает владения всеми уже находившимися в нём изменениями.
- Фоновый экспорт может продолжать писать файлы после завершения команды; это тоже активная работа владельца. Перед передачей убедиться, что собственных писателей/Unity-операций больше нет.

## Завершение и видимость

Исполнитель доводит свою задачу до требуемых проверок/доказательств, затем обновляет Notion и передаёт ресурс. Кратко сообщает результат, оставшиеся ограничения и при необходимости требуемое действие владельца. Менеджер передаёт владельцу существенные изменения, а не каждое подтверждение ожидания. Установленная роль не гарантирует постоянного фонового наблюдения.
