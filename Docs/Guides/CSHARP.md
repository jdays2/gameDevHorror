# C# и выбранная архитектура

## Песочница как пример разделения

Предел здоровья меняется у экземпляра PlayerLife2D, а зона тира помнит прежнее здоровье до выхода. Так обычный игрок не получает 100 HP во всех сценах, а посещение тира не лечит его снаружи. Мишени используют прежнего Сталкера: отдельный компонент фиксирует тело/запрещает укус, а разные 2/6/20 HP задаются профилями. Пуле не нужно знать, в какой комнате стоит цель. Геометрия и подписи хранятся в сцене и редактируются мышью; Editor-создатель не участвует в игровом запуске.

## После JavaScript

`class` описывает объект с данными/методами; `int`, `float`, `bool`, `string` задают тип заранее. Компилятор проверяет типы до запуска. `public` — доступ извне, `private` — внутреннее состояние. `[SerializeField] private` показывает поле в Inspector и сохраняет его, не открывая произвольную запись из других классов.

```csharp
[SerializeField] private EnemyDefinition definition;
private EnemyHealth2D health;
public int Health => health.Current;
```

`definition` — ссылка на asset, `health` — компонент конкретной особи. `Health => ...` — свойство чтения, не копия числа. Переименование сериализованного поля требует миграции/FormerlySerializedAs: обычный rename может потерять значения сцены.

## Компонент, prefab, сцена, asset

MonoBehaviour живёт на GameObject: мотор двигает тело, восприятие проверяет видимость, brain выбирает действие. Prefab сохраняет комплект компонентов/исходных ссылок. Сцена хранит экземпляры и overrides. ScriptableObject — общий asset настроек, используемый несколькими компонентами и отдельно редактируемый в Inspector.

Конфиг **не** хранит текущее HP. Если два врага ссылаются на Stalker-Default и записывать HP туда, ранение одного затронет всех. EnemyHealth2D.Initialize копирует начальное число в локальный Current. Aggro/State/таймеры также локальные.

## Почему композиция

Сталкер боится света, следующий враг злится на него. При наследовании всего Сталкера пришлось бы отключать чужие правила и переопределять большие методы. Вместо этого оба могут использовать EnemyHealth2D/EnemyMotor2D/EnemyPerception2D, но собственные решения. Это композиция — сборка из частей с определёнными обязанностями.

Машина состояний Сталкера остаётся явным switch: переходов пока немного, их легко видеть. Отдельный класс для каждого состояния только ради названия паттерна не нужен. Общие механики уже отделены от switch.

Damageable2D — общий контракт урона. Пуле достаточно вызвать ReceiveBulletHit/TryTakeDamage, не зная названия монстра. IThreatLight2D описывает защитный свет; обычная лампа автоматически им не становится. Абстракция вводится на реальной границе, не для каждой новой дальности фонаря.

## События и порядок

При смертельном уроне EnemyHealth2D один раз вызывает Died. Brain переводит врага в Dead и выключает столкновения. EnemyDeathEffects2D запускает кровь/разрыв независимо от AI. Завершение VFX не решает, жив ли враг. Подписка `+=` сопровождается отпиской `-=` при уничтожении.

Awake получает зависимости, FixedUpdate выполняет физический шаг, LateUpdate подходит для визуала/камеры после движения. Отдельный Update не антипаттерн. У общих модулей врага нет собственных циклов: их вызывает владелец решения. Дорогие поиски/аллокации/физические запросы важнее количества методов.

## Изменить и проверить

1. Остановить Play; найти asset/экземпляр, которому принадлежит значение.
2. Общие скорости — Data/Enemies, область конкретного патруля — экземпляр сцены.
3. Для разновидности Duplicate config и назначить копию нужным врагам. Изменение общего asset влияет на все ссылки, даже при редактировании в Play.
4. Не применять все overrides к prefab без разбора: локальные патрули можно случайно распространить на весь вид.
5. Изменение поведения проверять нужной регрессией, громкость — прослушиванием. Тест, повторяющий строку присваивания, мало помогает.

## Пример границ из текущего изменения

Раньше DemoLevelFlow2D одновременно выбирал текст, менял Canvas, останавливал Сталкеров и перезапускал сцену. Теперь правило цели находится в LevelDefinition, вычисление — LevelObjectiveController2D, Canvas — LevelCompletionView2D, завершение — LevelRunController2D. Если меняется текст задания, не приходится читать AI или код записи файлов.

В машине Сталкера switch выбирает StepIdle/StepPursuit/StepRecoil/StepRetreat/StepWait/StepAttack. Общий физический шаг по-прежнему один. Это выделение методов по смыслу, а не6 новых Update и не искусственное наследование. Проверки допуска атаки CanStart/CanBite названы по вопросу, на который отвечают.

`ICheckpointParticipant` позволяет другому компоненту реализовать три операции: Capture, Validate, Restore. Сохранение не требует цепочки проверок «если Сталкер, если следующий монстр…». `CheckpointData` отделяет данные файла от живых Unity-ссылок. Почему нужны постоянные ID и явные флаги присутствия — в [гайде чекпоинтов](CHECKPOINTS.md).

## Оружие: где полезно наследование

Помповый дробовик повторяет расход патрона и cooldown обычного WeaponCycle, но добавляет фазы Pumping/Loading. Поэтому PumpShotgunCycle наследует его, а PumpShotgunDefinition переопределяет создание цикла и веер. PlayerWeapon2D работает с общими свойствами/методами, не спрашивая «это дробовик?». Общий код попадания и HUD не приходится копировать.

Инвентарь использует композицию: содержит определения и отдельные циклы. Definition — общий рецепт; cycle — приготовленный по нему экземпляр со своими патронами и таймерами. Закрытые поля и операции TryFire/TryReload защищают правила: нельзя выстрелить при помпе или получить патрон из незаконченной вставки. Это инкапсуляция, а не просто раскладывание методов по файлам. Улучшения вместимости пока не реализованы.
