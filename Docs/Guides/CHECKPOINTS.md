# Чекпоинты: игра, настройка, C#

## Текущее состояние

FirstShift, его профиль и 8 volumes удалены по запросу владельца. В основной MechanicsSandbox нет checkpoint-контроллера: R всегда начинает чистый тест. Система сохранений и независимые тесты остаются; пользовательские старые слоты не удаляются. Раздел ниже описывает историческое поведение FirstShift, а не доступную сейчас сцену. Подключение сохранений к новой сцене требует её собственного LevelDefinition и явного авторинга.

## Историческое поведение FirstShift

Ранее: открыть FirstShift и нажать Play. Внутри8 помещений после входа стоят невидимые trigger volumes. При первом посещении такой точки появляется «Контрольная точка сохранена». Система ждёт окончания движения дверей и оседания разлёта; до подтверждения продолжает действовать предыдущий слот. Пока ждём, игра идёт, фиксируется состояние в момент фактической записи, а не пересечения порога. Если игрок умер раньше, новый снимок отменяется.

После смерти R перезагружает сцену и восстанавливает последнюю точку. При следующем запуске сцены слот также продолжается автоматически. Если слота ещё нет — обычное начало комнаты. Здоровье/патроны не пополняются: было2 HP и7 патронов — восстановится2 и7. Собранное остаётся собранным, убитое — убитым. Живой преследователь помнит агрессию; checkpoint не служит безопасной зоной.

После успешного выхода слот очищается; R начинает чистый уровень. Слоты раздельные по levelId. Отдельной кнопки «Продолжить»/меню кампании пока нет. BasementPrototype/LevelTemplate получили ID/адаптеры, но авто-чекпоинты включены только в FirstShift.

## Что восстанавливается

| Объект | Содержимое |
|---|---|
| Игрок | Позиция, направление/включение фонаря, фактическое HP, карты, оружие/contentId, патроны, суммарные модули и их количество |
| Лут | Собран/активен, остаток патронов частично подобранной коробки |
| Дверь | Открыта/закрыта, разблокирована; движение не проигрывается повторно |
| Сталкер | HP, постоянная агрессия, поворот изображения, состояние/его возраст, световая реакция, уклонение/отдача, cooldown/уже нанесённый укус, текущая мирная точка/пауза |
| Группа | Активирована ли; не активированные авторенные враги остаются ждать |
| Следы | Вариант, точные положения/размеры/цвета капель и частей. Никакой повторной крови или death-аудио при загрузке |
| Уровень | Время попытки, последняя и ранее посещённые точки |

Короткие вспышки, летящие пули, звук, разлёт до оседания, следы от попаданий/декоративные гильзы не входят в снимок. Камера сразу перемещается к восстановленному игроку. Для восстановления используется новая загрузка сцены; это не функция отмены произвольных изменений в уже работающем мире.

## Добавить точку / объект

1. Остановить Play. В отдельной сцене уровня создать/настроить LevelRunController2D, LevelObjectiveController2D и LevelCheckpointController2D с собственным LevelDefinition. К MechanicsSandbox эту процедуру без отдельного задания не применять.
2. Создать GameObject с BoxCollider2D (**Is Trigger**) и CheckpointVolume2D. Задать уникальный **Checkpoint Id** понятным постоянным словом и ссылку **Controller**. Поставить объём внутри входа, не за стеной; ширина должна перекрыть реальный проход. Cyan Gizmo виден при выделении.
3. Для новых дверей/лута/врагов выполнить **Emergency Shift → Levels → Prepare active level persistence**, затем сохранить сцену. Команда добавляет адаптеры и назначает уникальные scene-instance ID; комнаты/расстановку/баланс не регенерирует. У существующих объектов ID сохраняются, дубликаты после Ctrl+D получают новый ID.
4. Не делать Apply All Overrides со сценическим Persistent Id в prefab. Сам prefab не имеет личности; ID принадлежит размещённому экземпляру.
5. Для нового вида написать адаптер ICheckpointParticipant с уникальным SaveKey и проверкой payload, подключить его к prefab/авторингу. Общий загрузчик менять не нужно. Для динамических волн потребуется отдельная фабрика/устойчивый runtime-spawn ID; её пока нет.

Настройки — отдельный LevelDefinition новой сцены (старый `FirstShift.asset` удалён); weapon catalog — `Data/Levels/Weapons.asset`; каталог уровней — Campaign.asset. После копирования сцены нужен новый LevelDefinition с новым levelId, ссылками и записью в каталоге/Build Profiles. Не копировать ID уровня для новой локации.

## Файл и совместимость

Один JSON в `Application.persistentDataPath/Checkpoints/<levelId>.json`; предыдущая версия рядом `.bak`. Путь зависит от Company/Product в Player Settings. В Inspector у CheckpointController есть контекстное меню **Clear local checkpoint slot**: очистить сохранение для новой попытки. Это удаляет слот и backup, не сцену.

Формат DTO version1. Проверяются ID, набор компонентов, уровень и **Save Revision**. Если поменяли геометрию/контракт/порядок частей так, что старый снимок опасен, увеличьте Save Revision в LevelDefinition. Неизвестный/несовместимый файл отклоняется с сообщением; прежняя запись не затирается молча. Автоматического мигратора старых версий и автоматического восстановления .bak пока нет.

`--checkpoint-directory <absolute-folder>` у player перенаправляет слоты для изолированных проверок. Development probes используют отдельные временные файлы; реальные сохранения игрока не должны участвовать в тесте.

## Почему так написано

**ScriptableObject** похож на общий JSON-конфиг фронтенда. Он описывает баланс, но не хранит текущее состояние игры. **DTO** — простой объект данных для JSON: числа, строки, массивы, позиции; ссылок на GameObject в файле нет.

**PersistentEntity2D.Id** — аналог постоянного ключа записи. Имя в Hierarchy, индекс массива и GetEntityId для сохранения не подходят: они меняются между запусками. **ICheckpointParticipant** — контракт: компонент сам знает, как снять/проверить/восстановить свои данные. Загрузчик знает только контракт, а не разновидности монстров.

Сначала выполняется проверка всего снимка, затем восстановление. Dead восстанавливается без события Died, иначе повторно появились бы кровь и звук. Упаковка состояния отделена от файловой записи: CheckpointStore можно проверять на временной папке, не запуская целый бой. Unity JSON не сохраняет null обычного вложенного класса надёжным признаком отсутствия — поэтому initialized/hasRemains/hasPool/hasShadow записываются явно.

## Версия оружейного payload

Общий файл остаётся version1, ключ компонента — player.v1. Внутри PlayerCheckpoint2D теперь format2 и явный hasInventory: все подобранные оружия по contentId, выбранное оружие, общий/заряженный боезапас, фаза и оставшиеся таймеры cooldown/помпы/вставки. WeaponCatalog содержит пистолет и дробовик. Проверка всего инвентаря предшествует изменению живого состояния; неизвестные ID, повторные слоты и некорректные числа отклоняются.

Старый format1 с одним пистолетом продолжает читаться. Старый внутренний цикл с общим боезапасом мигрирует в магазин min(8,total) и резерв, без создания патронов. Новый цикл пистолета format2 хранит загрузку/остаток времени замены магазина; восстановление завершает её один раз без повторного стартового звука. Цикл дробовика сохранил format1. Это ограниченная совместимость конкретного payload, не универсальная миграция будущих форматов. В песочнице checkpoint-контроллер по-прежнему отсутствует. Регрессия оружия временно сохраняет данные в отдельный слот и восстанавливает после смерти/перезагрузки, не используя файлы игрока.
