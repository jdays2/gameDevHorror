# Рабочий паттерн проекта

Адаптация SOD: краткий индекс, текущий roadmap, контракт фичи, решения, активные реестры и отдельные свидетельства. Использовать владельцу и агенту при каждой работе по проекту.

## Начало задачи

1. Прочитать AGENTS/project skills, [индекс](../README.md), [порядок Notion](../NOTION_WORKFLOW.md), актуальный план и затронутые карточки в Notion. Затем связанную локальную SPEC/Features/Guides. Старые локальные планы — снимки, не текущая очередь.
2. Назвать ожидаемое поведение, границы и критерий готовности. Уже выданное поручение действует; повторное согласование одинакового шага не требуется. Нерешённый игровой выбор фиксируется карточкой типа «Вопрос» в Notion до зависимой реализации.
3. Проверить Git status и diff нужных файлов, пересечения с задачами/багами/вопросами Notion. Сохранить ручные изменения и план автора. Ссылка на будущий этап не означает, что его код готов.

## Где живёт информация

| Информация | Каноническое место |
|---|---|
| Продуктовые требования и принятые ограничения | SPEC; планы/идеи явно маркируются в GAME_CONCEPT |
| Текущий приоритет/следующий шаг | Планы Notion + связанные карточки задач |
| Контракт системы: владелец, данные, команды, зависимости | Features; UI/Enemies/Weapons/Guides содержат тематические детали/настройку |
| Общие слои и composition | ARCHITECTURE, нормы в skill/Conventions |
| Почему решение принято | Decisions/ADR-NNN, с фактическим статусом реализации |
| Сообщённый/воспроизводимый дефект | Баги Notion/BUG-NNN, наблюдение, воспроизведение, причина/проверка/статус |
| Известный долг/не выполненная система | Задачи Notion/BL-NNN; условия OPT-01 в связанном плане Notion |
| Не выбранный дизайн/контракт | Задачи Notion типа «Вопрос»/Q-NNN: варианты, последствия, решение автора |
| Метод проверки | VALIDATION |
| Результат на конкретной ревизии | Reports + JSON/изображения в Validation |
| Краткая история и релизы | Изменения и релизы Notion; локальные старые планы/Archive — исторические снимки |

Фича: назначение → текущая реализация → данные/владелец → команды/проверки → зависимости → ограничения и нужные решения. Шаблон — [Features/_template](../Features/_template.md). Технический аудит не превращать в новое игровое ТЗ.

## Во время и в конце шага

Меняется контракт/число/ID — обновить соответствующий источник и найти связанные упоминания; не дописывать противоречащую историю в конце документа. Подробности выполненных прогонов уносить в Reports с датой, ревизией, сценой/методом и ограничениями. Контракт не доказывается старым тестом после нового кода.

Без отдельного напоминания регистрировать новые сообщения/дефекты в базе «Баги» после проверки дубликатов и обновлять их при начале/завершении исправления. Отметить фактически завершённую работу и следующий шаг в карточках/плане Notion; добавить связанную запись в «Изменения и релизы». BUG закрывается воспроизведением и проверкой, Q — ответом владельца/ADR, BL — реализацией и проверками. ID не переиспользуются. Перед записью перечитать карточку, сохранить правки владельца и историю. Ручную приёмку автором агент не отмечает. Подробный протокол статусов, проверки ID и сбоев доступа — в NOTION_WORKFLOW.

Сообщить: что изменено, как проверено, что осталось/требует ручной оценки и состояние коммита. Отметка «ручной плейтест автора» принадлежит автору. Локальный коммит не равен push.

## Как владельцу давать следующую задачу

Достаточно указать: **фича/область; желаемое поведение; что сохранить; как поймём, что готово** — либо код/ссылку карточки Notion. Можно редактировать план/карточку Notion и локальный технический документ фичи вручную — агент должен прочитать эти правки. Новое сообщение о дефекте агент сам регистрирует в Notion. При существующей записи указать Q/BUG/BL; новые решения отражаются в локальном контракте/ADR и связанных карточках.

Не требуется читать все Reports, Changelog или Archive перед каждой задачей. Открывать их по конкретному ключу, регрессии или проверке прежнего решения. Текущий игровой контракт не назначается историческим отчётом.
