# Принятие skills и архитектуры SOD

Решение владельца от 2026-10-19: изучить репозиторий друга, установить его skills и заменить противоречащие им собственные архитектурные правила.

Последующее поручение той же даты: унифицировать всю документацию по этому паттерну, затем проверить и обновить весь собственный код. Это отдельный активный [этап 00](../Roadmap/00-ArchitectureMigration.md), BL-001; исходный перенос ниже описывает состояние до выполнения кодовой миграции.

Источник: [janitoooor/SOD](https://github.com/janitoooor/SOD/tree/1479eec1bf8dc133093be05de164b46a6078e789), commit `1479eec1bf8dc133093be05de164b46a6078e789`. Перенос закреплён на этой версии; будущий update требует новой сверки. Точные пути и SHA-256 файлов — в [SOD_SKILLS_SOURCE.json](SOD_SKILLS_SOURCE.json).

## Что установлено

Пять upstream skills перенесены без правок, со всеми references/resources:

| Skill | Назначение | Применение у нас |
|---|---|---|
| unity-pipeline | Команды живого Editor, компиляция, тесты, выполнение проектных scripts | Основной новый канал управления Unity; имена и аргументы сверяются с реальным каталогом |
| unity-package-management | Работа с UPM и подбор пакетов | По задаче; уже открытый проект не запускается вторым Editor |
| ui | Выбор UI-фреймворка | Следовать текущему UI конкретной сцены/фичи |
| ui-ugui | Canvas, RectTransform, layout, ScrollView | Наш игровой UI — uGUI; не пересобирать пользовательский Canvas ради общего примера |
| physics-3d-collision | Диагностика PhysX 3D | Для 3D-проектов; не выдавать его правила за контракт Physics2D Emergency Shift |

Файлы находятся в `.agents/skills/` проекта и личной библиотеке `~/.codex/skills/`; последняя делает их доступными будущим проектам. Codex обнаруживает новые skills со следующего хода. В этом ходе инструкции уже прочитаны и могут применяться явно. Изменения одной копии должны синхронизироваться с другой.

## Архитектура — отдельно от пяти skills

В исходнике архитектура описана в `.cursor/rules/`, а не в пяти SKILL.md. Создан шестой переносимый skill [sod-unity-architecture](../../.agents/skills/sod-unity-architecture/SKILL.md), который подключён к AGENTS.md и установлен в личную библиотеку.

Он принимает MVC по фичам, чистую C# Model, Controller/команды, отдельные View/Unity-адаптеры, SOLID, композицию, ограничения constructor dependencies, неизменяемые SO-конфиги, Zenject/Extenject, отсутствие mutable-глобального состояния, устойчивые ID, версионированные DTO/миграции и EditMode-тесты моделей. Перенесены также правила срока жизни подписок/async/кешей, горячих циклов, Input Actions, контракта анимаций и границы авторитетной симуляции.

Для проверки смысла правил просмотрены `Docs/Architecture.md`, `Docs/Conventions.md` и реальные примеры SOD: GameClock/GameClockData, TimeInstaller, GameClockPresenter и ModifyStatCommand. У источника тоже есть описанный долг: PlayerMovementView ещё совмещает мотор, ввод и представление. Правила целевой архитектуры не доказывают, что весь SOD уже им соответствует.

## Какие старые правила удалены или заменены

| Наше прежнее правило | Принятое правило SOD |
|---|---|
| Не вводить DI без измеренной необходимости | Zenject/Extenject — целевая композиция, с явным этапом установки/миграции |
| Prefab/scene/Configure как основной способ передачи зависимостей | Constructor injection и installer фичи; прежняя проводка — legacy до миграции |
| Нет ориентиров размера/зависимостей | Ориентир 200–300 строк; предпочтительно 2 зависимости, 3 в исключении, до 5 у делегирующего координатора; installers без лимита |
| Runtime только по техническим обязанностям | При новых фичах/миграции Config/Logic/View, команды и отдельный motor/environment adapter под существующим production root |
| Прежние общие советы как верхний архитектурный стандарт | Архитектура SOD имеет приоритет по прямому поручению владельца |

Противоречащие строки удалены из workflow/unity-migration и references; эти skills остаются как правила сохранности Emergency Shift. Content-library не конфликтует с SOD и сохранён. Старый отказ от жёстких лимитов в обзоре других репозиториев помечен как заменённый новым решением, а не оставлен второй нормой.

## Границы адаптации

- Пути SOD `Assets/_Project` заменяются смысловыми границами под `Assets/EmergencyShift`; существующие ассеты и GUID не перемещаются.
- Первый вид камеры, survival-механики, чужие игровые референсы, расписание недель и SOD ADR-номера не становятся требованиями Emergency Shift.
- Steam co-op, Mirror, dedicated server, запрет игровой паузы и конкретные save-триггеры — решения другого продукта. Сохраняются чистая симуляция, отдельное состояние игрока, ID и адаптеры; одиночные диалоги/пауза и локальные чекпоинты нашего проекта не меняются.
- Строка upstream о приоритете проекта над пользовательскими инструкциями не переносится как действующая иерархия. Инструкции человека и системные ограничения сохраняют свой настоящий приоритет.
- Повторные согласования из source workflow не отменяют уже выданное поручение пользователя. Согласованные действия выполняются; нерешённый дизайн поднимается отдельно.
- Upstream skills сохранены дословно. Их технические примеры сверяются с фактическими инструментами; имена/аргументы версионируются. Ограничение `eval` диагностикой и сохранность ручных сцен применяются через наш routing.
- В корне просмотренного commit не найден общий LICENSE на правила. Ссылка на автора и исходный commit сохранены; это запрошенная владельцем локальная установка, а не заявление о лицензии сторонних игровых ассетов SOD. Игровые ассеты/пакеты друга в Emergency Shift не импортируются.

## Фактический статус

Установлен официальный `com.unity.pipeline@0.8.0-exp.1` из Unity registry. Открытый Unity `6000.6.5f1` загрузил пакет после выхода из Play и Refresh. `unity status` и `editor_status` вернули ready; `console_status`: `compilationFailed=false`, текущих consoleErrors=0. Read-only eval вернул наш production root и `Assets/EmergencyShift/Scenes/MorgueRouteTest.unity`. Сцена dirty; сохранение не выполнялось. Это тест интеграции пакета, не подтверждение полного игрового прогона.

Повторная диагностика уже с `--skill unity-pipeline` успешна, compile errors=0. Pipeline предупреждает об отсутствии RuntimePipelineConfig: в Player builds его сервер отключён; управление Editor работает. Runtime-сервер в сборке этой задачей не включался. Предупреждения legacy MCP о повторном соединении также не являются ошибкой компиляции.

Все девять проектных skills прошли штатный `skill-creator/scripts/quick_validate.py`; использован уже имеющийся PyYAML без установки нового окружения. Пять upstream каталогов сверены с Git blobs закреплённого commit, локальные/личные копии проверены по SHA-256. Проверка whitespace ограничена файлами этого переноса; чужие незавершённые Unity YAML не форматировались.

При исходном переносе skills Zenject ещё не был установлен. Следующим кодовым шагом подключён Extenject, введены первые границы [здоровья](../Features/Health.md), [ввода и композиции](../Features/PlayerInput.md). MVC/команды ещё не внедрены во все существующие системы. Реальные ограничения продолжают учитываться в [ENGINEERING_REVIEW](../ENGINEERING_REVIEW.md).

Резервная копия прежних проектных skills/правил и рабочих diff сохранена вне активного обнаружения skills: `work/sod-adoption-2026-10-19/` в папке чата. Исходные правила до замены также остаются в Git. Чужие незавершённые изменения не включаются в коммит этого переноса.
