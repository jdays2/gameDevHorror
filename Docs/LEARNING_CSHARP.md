# C# и Unity: последовательный гайд на нашем проекте

Этот гайд растёт вместе с игрой. Сначала прочитай уроки 1–3, затем открой `PlayerMotor2D.cs`. UI Unity уже знаком, поэтому акцент на коде и связях.

## 1. Что запускает код

В браузере JavaScript запускается страницей и обрабатывает события. В Unity движок вызывает методы компонентов. `GameObject` — объект в Hierarchy; компонент — поведение или возможность объекта. На Player находятся физическое тело, коллайдер и несколько наших компонентов.

```csharp
public sealed class PlayerMotor2D : MonoBehaviour
{
    private void Update()
    {
        // Unity вызывает этот метод каждый кадр, пока компонент активен.
    }
}
```

`class` определяет тип компонента. `: MonoBehaviour` даёт ему возможность быть прикреплённым к GameObject и получать вызовы Unity. `sealed` запрещает наследование от этого класса: нам не нужна иерархия типов движения. Имя класса компонента совпадает с именем файла.

`namespace EmergencyShift` группирует наши типы и защищает от совпадений имён с пакетами. `using UnityEngine` позволяет писать `Vector2`, а не `UnityEngine.Vector2`.

## 2. Переменные, типы и доступ

В C# тип переменной определён при компиляции. `float` — дробное число, `bool` — true/false, `Vector2` — пара x/y, `Rigidbody2D` — ссылка на компонент физики. `var` также имеет конкретный тип, просто компилятор выводит его из правой части.

```csharp
[SerializeField, Min(0.1f)] private float moveSpeed = 3.5f;
```

`private` означает, что другие компоненты не меняют поле напрямую. `[SerializeField]` сохраняет значение в сцене/префабе и показывает его в Inspector. `Min` помогает не выставить отрицательную скорость. Суффикс `f` сообщает, что число имеет тип float.

Важное отличие от обычной переменной в новом объекте: для существующего компонента Unity берёт сохранённое значение Inspector. Изменение `3.5f` в файле не обязательно изменит ранее сохранённый экземпляр.

`public bool IsOn => beam != null && beam.enabled;` — свойство для чтения. HUD может узнать состояние фонаря, не получая свободный доступ к его внутренним полям.

## 3. Жизненный цикл

| Метод | Когда вызывается | Зачем в нашем коде |
|---|---|---|
| `Awake` | При загрузке экземпляра | Получить Rigidbody2D, запомнить положение закрытой двери |
| `Update` | Каждый кадр | Прочитать клавиши и мышь, обновить подсказки |
| `FixedUpdate` | На шагах физической симуляции | Задать скорость физического тела |
| `LateUpdate` | После обычных Update | Переместить камеру вслед за игроком |
| `OnDisable` | При отключении компонента | Остановить движение |

Частота кадров и частота физики могут различаться. Поэтому ввод и физическое движение разделены. Если вручную менять Transform физического игрока каждый кадр, можно получить рывки и неудобные столкновения.

## 4. Разбираем движение

Открой `PlayerMotor2D.cs`.

1. `[RequireComponent(typeof(Rigidbody2D))]` говорит Unity, что этому поведению нужно физическое тело.
2. `GetComponent<Rigidbody2D>()` получает компонент того же GameObject. Сохраняем ссылку один раз в Awake.
3. `Keyboard.current` получает текущую клавиатуру. Проверка `null` позволяет пережить отсутствие устройства.
4. Тернарный оператор `условие ? значение_если_да : значение_если_нет` преобразует нажатие в 1 или 0. D минус A даёт горизонтальное направление.
5. `new Vector2(x, y).normalized` ограничивает длину направления единицей. Без этого W+D дают длину √2 и движение быстрее.
6. `body.linearVelocity = movement * moveSpeed` задаёт скорость в единицах мира в секунду. Умножать её на deltaTime не нужно: интеграцию выполняет физика.

**Первое упражнение:** останови Play, выбери Player, в Inspector поменяй Move Speed с 3.5 на 2, снова запусти. Это изменение экземпляра сцены; файл C# менять не требуется.

## 5. Разбираем фонарь

Открой `Flashlight2D.cs`. Ссылки `worldCamera`, `aimPivot` и `beam` соединяют поведение с конкретными объектами сцены.

Координаты мыши измеряются в пикселях окна. `ScreenToWorldPoint` переводит их в координаты мира. Вычитаем положение игрока, чтобы получить направление. `Atan2` даёт угол; преобразуем радианы в градусы. Вычитаем 90 градусов, поскольку локальное направление фонаря — вверх.

`wasPressedThisFrame` истинно только в кадре нажатия. `isPressed` остаётся истинно всё время удержания. Поэтому движение использует isPressed, а переключение F — wasPressedThisFrame.

**Упражнение:** останови Play, выбери Player и поменяй `Range` у компонента `Flashlight2D`. Это дальность света, а не скорость или масштаб капсулы. В v0.2 компонент управляет радиусом луча сам: ручное изменение Outer Radius дочернего Light2D будет заменено параметрами компонента при запуске.

## 6. Разбираем дверь и coroutine

`Door2D` хранит ссылку на створку. Створка содержит картинку, Collider2D и ShadowCaster2D: все три следуют за её Transform.

`StartCoroutine(Slide(...))` запускает действие, растянутое по кадрам. `IEnumerator` позволяет методу приостанавливаться через `yield return null`. Это не отдельный поток: действие продолжается на следующих кадрах Unity. `Time.deltaTime` сообщает длительность кадра; здесь оно нужно, потому что мы сами считаем время анимации.

`moving` запрещает повторное переключение во время перемещения. `Vector3.Lerp` вычисляет промежуточное положение, а `SmoothStep` смягчает начало и конец движения.

**Упражнение:** останови Play и поменяй Duration двери. Проверь, что проход освобождается вместе со створкой.

## 7. Кто кому сообщает состояние

`PlayerInteraction` выбирает близкую дверь и вызывает её `Toggle()`. `PrototypeHud` читает `CurrentDoor` и `IsOn`. Игрок и дверь ничего не знают о текстовых надписях. Поэтому будущая замена UI не требует переписывать движение.

Прямые ссылки похожи на явно переданные зависимости во фронтенде. Однако компоненты Unity не пересоздаются при каждом отображении состояния: они живут на объектах сцены, а Update меняет их данные и представление.

Пока HUD читает состояние каждый кадр — для пары строк это просто и достаточно. События понадобятся, если появится много независимых подписчиков; добавлять их заранее не обязательно.

## 8. Почему нет «суперархитектуры»

Общая система взаимодействий полезна, когда появляются несколько разных взаимодействий. Singleton полезен только при действительно общей сущности с ясным жизненным циклом. Сейчас эти конструкции добавили бы новые понятия без решения текущей задачи. Мы выбираем архитектуру по уже существующему поведению.

Следующий урок будем добавлять после следующего расширения: сначала новая потребность, затем решение, затем объяснение на изменившемся коде.

## 9. Параметры фонаря и будущие улучшения

В v0.2 у фонаря есть два источника: направленный луч и очень слабая круговая подсветка у ног. Они уже находятся в префабе, а `Toggle()` включает и выключает их вместе. Игровой код не создаёт их заново.

`range` и `beamAngle` — сериализованные поля, которые дизайнер меняет в Inspector. `Range` и `BeamAngle` — публичные свойства только для чтения. Это позволяет другим компонентам узнать настройки, не меняя внутреннее состояние напрямую.

```csharp
// Пример вызова из будущего предмета улучшения:
flashlight.SetOptics(5.5f, flashlight.BeamAngle);
```

Этот вызов увеличивает дальность, сохраняя угол. Метод применяет допустимые значения и обновляет Light2D. Предмету не нужно знать, как называются дочерние объекты фонаря. Самих предметов улучшений пока нет — это точка для следующего этапа.

`OnValidate()` помогает увидеть изменения параметров в редакторе. `Awake()` применяет сохранённые настройки при запуске. Полный внешний угол сейчас 80 градусов, внутренний — 60% от него, то есть 48 градусов. Разница даёт плавный переход к тёмным краям.

Дальность измеряется в единицах мира; разрешение текстуры света — в пикселях. Первое изменяет игровой обзор, второе влияет на гладкость изображения. Это разные параметры.

## 10. Почему на стыках появлялись выступы

Форма препятствия, освещённая поверхность и проекция тени обрабатываются раздельно. Если непрозрачная стена исключается из собственного затенения, на её пересечении с соседними стенами могут быть видны лишние освещённые участки. Для текущего каркаса непрозрачные стены и дверь используют `Cast and Self Shadow`.

Ещё один важный размер — положение источника. Луч был смещён на 0.35 единицы от центра, а минимальная полуширина коллайдера капсулы — 0.28. У боковой стены источник мог оказаться внутри препятствия. Смещение уменьшено до 0.18. Свет должен оставаться с доступной стороны стены даже при подходе вплотную.

Это показывает, почему сначала проверяем простую геометрию: на ней легче заметить несоответствие размеров и правила затенения до появления художественных спрайтов.

## 11. Вход в Play и чистое начальное состояние

Шаблон Unity использовал ускоренный вход в Play без перезагрузки кода и сцены. Такие настройки требуют внимательно управлять состоянием между запусками. Для первого проекта включена обычная перезагрузка: новый Play начинается из сохранённой сцены, вызываются методы инициализации и не требуется вручную возвращать дверь, фонарь и временные состояния проверки.

Настройка находится в Project Settings → Editor → Enter Play Mode Settings. Быстрый режим можно вернуть позже, когда появится явная процедура сброса состояния. Это настройка редактора, а не дополнительная механика игры.

## 12. В каком порядке писать новую механику

План следующей разработки находится в `MVP_PLAN.md`. Код становится понятнее, когда каждая новая часть решает наблюдаемую задачу: сначала цель определяет, что находится в луче; затем монстр использует это правило; затем карта даёт доступ к двери; после появления прогресса его сохраняем.

Для одной задачи порядок такой: поведение → данные → небольшой компонент → ссылки в сцене → обычный и ошибочный сценарий → перезапуск → объяснение кода. Например, задачу «карточка открывает дверь» проверяем без здоровья, патронов и большого экрана инвентаря.

Общий контракт взаимодействия имеет смысл, когда появляются дверь и подбираемая находка. Система сохранения — когда реально есть найденные предметы и завершённые румы. Такой порядок помогает понять, зачем существует каждый класс, и не заставляет изучать абстракции до появления задачи для них.

## 13. Визуальное поведение: взгляд врага

Глаз и зрачок стоит разделить на два визуальных элемента. Последовательность спрайтов меняет позу тела и закрывает веко; небольшой отдельный компонент смещает зрачок внутри открытого глаза в направлении игрока. Направление берётся от центра глаза к цели, а расстояние движения ограничено радиусом радужки. Когда веко закрыто, зрачок не отображается.

Это пример разделения ответственности: AI решает, кого враг обнаружил и преследует, а визуальное поведение показывает, куда он смотрит. Взгляд не даёт обнаружения сквозь стены. Не нужно рисовать новые кадры шага для каждого направления зрачка. Теперь это реализовано в `StalkerSpriteAnimator.cs` и показано также в `../VisualConcepts/v05/preview.html`.

## 14. Состояния существа — enum и switch

`BehaviourState` перечисляет возможные состояния: подкрадывание, сжатие, отход, пауза, атака и смерть. Это `enum`: переменная хранит одно значение из заданного списка. `switch` в `FixedUpdate()` выполняет поведение текущего состояния. Метод `Enter()` меняет состояние и обнуляет его таймер. Так правила переходов можно прочитать в одном компоненте.

`exposureTime` складывает время близкого непрерывного света. Если луч ушёл, число снова ноль. Дистанция и задержка — поля Inspector; значения конкретного экземпляра могут отличаться от начальных чисел в C#. Изменение спрайтов не должно сбрасывать эти настройки.

## 15. Спрайт, центр и взгляд

`StalkerSpriteAnimator` читает состояние врага и меняет `bodyRenderer.sprite`. Массив `Sprite[]` — упорядоченный список кадров. Счётчик времени и частота задают индекс кадра. При смерти индекс доходит до последнего и остаётся там, а не замыкается в живой цикл.

Pivot — точка, которой кадр привязан к объекту. Если в разных кадрах она соответствует разным местам тела, изображение будет дёргаться при неподвижном объекте. В нашей нарезке pivot совпадает с глазом. Метаданные Rect важны не меньше рисунка: равные ячейки обрезали одну ногу и добавляли её кусок соседу.

Зрачок — дочерний SpriteRenderer. Направление к игроку переводится в локальные координаты повёрнутого изображения; смещение ограничено радиусом. Это небольшой математический эффект поверх кадров, поэтому не нужны десятки рисунков взгляда.

## 16. Один укус — одно попадание

Атака длится много кадров. Без `strikeApplied` проверка расстояния снимала бы здоровье на каждом кадре. Флаг отмечает, что укус уже применён, и сбрасывается при начале следующей атаки. Перед уроном ещё проверяется стена между существом и игроком.

`PlayerLife2D.TakeDamage(1)` меняет здоровье через метод. Свойство `Health` читается снаружи, но изменяется внутри компонента. При нуле отключаются движение, взаимодействие, свет и физическое участие капсулы; компонент жизни остаётся включён, чтобы прочитать R и перезапустить сцену.

## 17. Зачем кровь отделена от врага

Враг знает, когда погиб, и один раз запускает `GoreBurst2D`. Лужа отвечает за форму следа, кусок — за своё движение. Другому существу можно назначить тот же префаб крови и другие спрайты фрагментов. Кровь не должна зависеть от количества кадров смерти или исчезать вместе с отключением AI.

У `BloodPool2D` свой seed — число, из которого получается раскладка. `System.Random` даёт разные размеры и повороты; несколько больших пятен соединяются в лужу, маленькие становятся каплями. `GibMotion2D` уменьшает скорость со временем и выключает обновление, когда кусок остановился. Это простой первый эффект, без симуляции жидкости.

## 18. Проверка и запись отличаются от игры

`StalkerCombatSetup` находится в Editor: он импортирует данные и сохраняет префабы/ссылки, а не генерирует комнату при старте. `StalkerDemoRecorder` добавляется только во время Play и весь закрыт условием `UNITY_EDITOR`: код нужен для записи, в обычную сборку не включается. Настройка окна Game View вынесена отдельно в Editor, потому что редакторский MonoBehaviour нельзя использовать как обычный игровой компонент.

В демонстрации капсула движется по сценарию, а AI/физика/анимации работают в Unity. Подсветка для осмотра, временное отключение ранних атак и тестовый урон указаны в отчёте. Скриптовая проверка не заменяет визуальный просмотр результата.

## 19. Почему тестовый труп — отдельный префаб

Для проверки месива не нужен живой враг, который умирает при каждом запуске. `StalkerRemainsTest.prefab` содержит только изображения останков и BloodPool. У него нет AI, здоровья и коллайдера: это видимый объект окружения, через который капсула может пройти.

`StalkerCorpseSetup.Add()` выполняется в редакторе, создаёт четыре экземпляра и сохраняет их трансформации/цвета. В `Play` эти данные уже загружены из сцены. Один префаб задаёт состав объекта; отдельные экземпляры отличаются поворотом тела, расположением частей и seed лужи. В будущем разные рисунки останков дадут дополнительное разнообразие; сейчас они лишь записаны в требованиях.

Кровь и пол имеют одинаковый sortingOrder, поэтому кровь смещена к камере на 0.02 по Z, как в обычном `GoreBurst2D`. Это только порядок изображения, не высота физического препятствия. Тело/куски выводятся группой с sortingOrder 1. При равных значениях порядка нужно проверять перекрытие визуально: наличие SpriteRenderer и правильной ссылки ещё не гарантирует видимость.

## 20. Затемнение, слои и случайный seed

`SpriteRenderer.color` умножает цвет рисунка. Множитель (0.58,0.55,0.60) затемняет останки без создания отдельной тёмной PNG; alpha остаётся 1. `RemainsVisualStyle` хранит общее правило для тела и кусков. Это статический класс: его не добавляют на GameObject, к данным обращаются по имени класса.

`SortingGroup.sortingOrder` определяет порядок целой составной фигуры. У живого врага 1, у мёртвого 0: живой всегда поверх останков, независимо от того, кто появился раньше. Смещение останков Z=-0.03 отделяет их от пола, поскольку пол тоже имеет порядок 0. Физика остаётся 2D; смещение используется для отрисовки.

`Kill()` переводит врага в Dead и сразу вызывает `GoreBurst2D.Play`. Лужа создаётся синхронно внутри Play; только части ждут 0.45 с в корутине. Новый seed задаёт случайную раскладку пятен/капель; общий размер тоже немного меняется. С одинаковым seed и размером форма повторяема — это полезно для будущих сохранений. Флаг emitted защищает от повторного создания.

При новой палитре Sprite-ассет сохранён с прежним GUID через редакторский CopySerialized. Ссылки сцены продолжают указывать на тот же ассет, хотя его текстура, Rect и pivot обновлены. Поэтому изменение картинки не требует перенастройки AI и здоровья.

## 21. Почему тени отделены от рисунка и AI

`CreatureGroundShadow2D` управляет двумя SpriteRenderer, уже сохранёнными в префабе. В v0.4.4 он копирует текущий спрайт тела и его поворот: тень повторяет все ноги и каждую позу. Шейдер берёт прозрачность рисунка, окрашивает силуэт чёрным и вытягивает направленную проекцию от фонаря. Прежние мягкие овалы больше не используются. Отдельный компонент позволяет выключить тени для сравнения, не отключая анимацию и поведение врага.

Направление тени — нормализованный вектор от источника фонаря к существу. Нормализация сохраняет направление, задавая длину 1. Другие числа определяют длину самой проекции. Чем ближе к концу луча, тем слабее тень; linecast не даёт форме пройти через стену. Оба запроса читают данные сцены, но не создают коллайдер и не меняют правила обнаружения.

`LateUpdate` применяется после движения; `[DefaultExecutionOrder(30)]` ставит обновление теней после обычного аниматора. Так тень следует за актуальным поворотом корпуса. После смерти компонент скрывает проекцию, завершает оседание контактной формы и перестаёт пересчитывать её.

Это имитация объёма в 2D. Настоящий ShadowCaster2D тоже был проверен, но дал длинный непрозрачный клин и скрыл часть второго врага. Здесь важно сохранять читаемость группы, поэтому выбран короткий полупрозрачный эффект. Метод не моделирует высоту каждой ноги.

## 22. Один материал, разные тени

Материал ссылается на шейдер — программу отрисовки. Два объекта могут использовать общий материал, но иметь разные параметры направления, длины и отсечения. `MaterialPropertyBlock` передаёт эти числа отдельному SpriteRenderer, не создавая копию материала на каждом кадре. Блоки создаются один раз и затем переиспользуются. Это не доказательство производительности толпы: её проверим отдельно в Profiler.

Текстура спрайта содержит RGB и alpha. RGB задаёт цвет, alpha — прозрачность. Для тени нужна только alpha: силуэт остаётся связанным с анимацией, а бледный цвет кожи не попадает в тень. Шейдер обрезает проекцию по границам луча и плоскости ближайшего препятствия; это ограниченная декоративная модель, не трёхмерная симуляция ног.

## 23. Предмет: данные и экземпляр

В v0.5 первый предмет реализован компонентом `FlashlightUpgradePickup`. Его настройки хранятся в префабе, а каждая копия имеет свой флаг collected. Концепт `FLASHLIGHT_AND_LOOT.md` предлагает позднее ItemDefinition как ScriptableObject-каталог, похожий на общую конфигурацию во фронтенде. Для единственного вида лута отдельный каталог пока не нужен.

Флаг «подобран» нельзя записывать в общее описание: тогда подбор одной линзы изменит другую. Установленные улучшения принадлежат игроку. Небольшой `IInteractable` уже позволяет двери и предмету сообщать подсказку и выполнять действие через единый выбор цели по E. Это оправдано появлением второго типа взаимодействия; большой универсальный инвентарь для одной линзы пока не нужен.

## 24. Почему мы не заменяем класс света

`Flashlight2D` — класс, описывающий поведение. Компонент на Player — его экземпляр со своими значениями range/beamAngle. Улучшение меняет эти значения через публичный SetOptics, сохраняя тот же экземпляр, Light2D и состояние F. Создавать новый класс под каждый уровень фонаря означало бы дублировать управление и ссылки без пользы.

`FlashlightUpgrades` запоминает базу в Awake и хранит `Dictionary<string, Vector2>`: ID вида → накопленные бонусы дальности/угла. Dictionary похож на Map в JavaScript. HasModule проверяет ключ; TryInstall возвращает bool и через `out string message` передаёт уведомление. При ошибке предмет остаётся. При успехе бонусы пересчитываются от базы, предмет выключается. В v0.5.2 Repeatable=true допускает несколько копий одного ID; false сохраняет режим уникального модуля.

`collected` и `repeatable` отвечают за разные вещи: конкретный предмет исчезает однократно, но следующий предмет того же вида может дать ещё бонус. Сумма ограничена полями Maximum Range/Angle игрока; после трёх стандартных находок база 4.2/80 превращается в 6.0/98. Поля бонусов принадлежат предмету, общие пределы — игроку. Это позволяет менять баланс в Inspector без новых классов.

Сами предметы не читают клавишу E. PlayerInteraction выбирает одну доступную цель и вызывает её Interact; так два близких предмета и дверь не срабатывают вместе. CircleCollider2D в режиме trigger помогает найти предмет, но не останавливает Rigidbody2D игрока. Общая инструкция по расстановке — FLASHLIGHT_UPGRADE_GUIDE.md.

`[SerializeField]` показывает private-поле в Inspector и сохраняет его вместе со сценой/префабом. Поле на экземпляре можно переопределить: например, Angle Bonus=15 и другой Module Id превращают копию в отдельный модуль угла. Изменения во время Play не записывают постоянный прогресс; он появится вместе с будущими контрольными точками.

## 25. Оружие, лут и общие данные эффектов

HasWeapon/Ammo принадлежат PlayerWeapon2D. WeaponLootPickup отвечает за объект на земле: его Interact вызывает Acquire или TryAddAmmo. HUD только читает числа. Так изменение рисунка коробки не ломает стрельбу, а скрытие счётчика до находки не меняет запас.

Три визуальных варианта лежат в ShotVisualProfile — ScriptableObject. Это общий конфигурационный объект: один профиль можно назначить всем пулям, не копируя значения в каждый префаб. Состояние игрока в него не записываем. Теперь эта форма хранения оправдана тремя реальными наборами данных; для одного апгрейда фонаря она была преждевременна.

BulletProjectile2D двигает изображение и проверяет путь через CircleCast в FixedUpdate. Проверка только точки назначения могла пропустить тонкую стену между кадрами; здесь проверяется весь отрезок и ближайшее попадание. Триггеры подбора не препятствия; собственный игрок исключён. При попадании вызывается уже существующий метод TakeDamage: оружие не знает устройства крови/анимации смерти.

ShotEffect2D отдельно затухает и удаляется. Пуля тоже имеет конечную жизнь. Для одного полуавтоматического пистолета простое Instantiate/Destroy достаточно как первый вариант; будущий автомат/толпа потребует измерений и возможного пула. Gameplay-классы не используют UnityEditor; подготовка ассетов/сцены находится в Editor. Recorder закрыт UNITY_EDITOR и отсутствует в обычной сборке.

В прототипе одно нажатие ЛКМ снимает один патрон. nextShot хранит время следующего разрешённого выстрела; повторный вызов в том же кадре ничего не тратит. Нулевой запас и мёртвый игрок также отказывают до создания эффектов. Магазин/перезарядку добавляем отдельной задачей, поэтому R остаётся перезапуском после смерти.

## Практика чтения ошибок

В v0.5.3 убрали вызов ShowNotification и числа из GetPrompt предмета. TryInstall продолжает менять оптику: игровое действие и его текстовое представление независимы, поэтому для упрощения UI не приходится менять расчёт бонусов.

Если текст E существует и active в Canvas, но его не видно, проблема может быть в представлении редактора: Game View показывает лишь увеличенный фрагмент кадра. Fit Game View изменяет редакторский zoom, а не Camera. Сначала проверяем данные/ссылки/active, затем масштаб просмотра; не меняем радиус взаимодействия ради исправления обрезанного UI.

Сообщение `error CS...` — ошибка компиляции C#: игра не готова к запуску, пока её не исправим. `NullReferenceException` означает, что код обращается к отсутствующей ссылке; сначала проверяем назначенные поля Inspector. Сообщение о неинициализированной лицензии относится к запуску редактора и не доказывает ошибку нашего кода.
