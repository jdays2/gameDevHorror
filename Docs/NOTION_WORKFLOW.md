## Начало каждой проектной задачи

1. Прочитать AGENTS, обязательные project skills и Docs/README.md.
2. Через подключение Notion прочитать главную страницу, текущий план, указанную карточку и связанные планы/баги. При новой задаче найти пересечения по области и критериям. Проверять данные перед началом, не полагаться на прежний текст чата.
3. Прочитать соответствующие локальные SPEC/Features/Guides и осмотреть реальный код. Назвать критерии готовности и сохраняемые ограничения. План описывает работу, локальная спека — обязательное поведение.
4. Для работы по существующей карточке обновить её статус при фактическом начале. Предложения/отложенные задачи не запускаются одной записью в доске. Не выдумывать даты, исполнителей и номера версий.

## Обязательный цикл бага

- Сообщение владельца об ошибке или обнаруженный дефект регистрировать в базе «Баги» в рамках текущей работы, без отдельного поручения «заведи баг». Сначала искать дубликат по ID, сцене/области и симптомам. Повторное проявление дополняет/переоткрывает ту же карточку.
- Новая запись: следующий свободный BUG-NNN после сверки существующих кодов; название, источник/ревизия/сцена, шаги, ожидание и факт, воспроизводимость, область, причина только если доказана. Перед созданием ещё раз проверить ID/дубликат. При параллельной работе сверить коллизию после записи, не обещать атомарность такого распределения номеров.
- Состояния: **Новая → В работе → На проверке → Исправлена**. Дополнительные: **Нужно уточнить**, **Заблокирована**, **Не воспроизводится**. Сообщение без воспроизведения допустимо сохранить как «Нужно уточнить» с исходным наблюдением, без доказанной причины.
- Перед исправлением — «В работе». После изменения сохранить решение, метод/результат проверки и фактический коммит. «Исправлена» означает проверку исходного сценария; при непроверенном сценарии или необходимой авторской оценке оставить «На проверке»/явное ограничение. Не закрывать по одной компиляции.
- Если есть отдельная задача реализации, связать её свойством «Баг»; описание дефекта остаётся в карточке BUG. После подтверждённого исправления обновить связанную задачу и ченджлог. Сохранить историю и исходное наблюдение.

## Завершение задачи

Перечитать изменяемую карточку перед записью. Вносить целевые изменения, сохраняя правки владельца; конфликт требований уточнять. Обновить статус, критерии, оставшиеся ограничения и ссылки на коммит/Reports. При изменении поведения обновить локальный контракт фичи. В «Изменения и релизы» добавить одно содержательное событие, связав задачу/баг; не дублировать уже записанный результат при повторном запуске. Ручную приёмку владельца агент за него не отмечает.

Тип «Релиз» используется только для реально подготовленной версии со своим составом, коммитом/сборкой, проверками и известными ограничениями. Перенос задач в «Готово» не публикует релиз. Подробные тестовые данные остаются в Reports/Validation; в Notion хранится краткий итог и адрес.

## Доступ и ошибки записи

Интеграция работает во время задач агента. Фонового наблюдателя, автоматического запуска кода от правок страницы и двустороннего зеркалирования Markdown нет. При недоступном Notion нельзя считать старый снимок актуальным или писать параллельный локальный roadmap. Если зависимые требования нельзя установить — сообщить препятствие; независимую разрешённую работу можно продолжать.

Неуспешную запись не объявлять сохранённой. Сохранить результат кода и перечислить несинхронизированные записи в ответе; при восстановлении доступа сверить состояние и дописать только недостающее. Не терять выполненную работу ради сбоя внешнего сервиса.
