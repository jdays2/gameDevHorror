# Проба освещения мебели

Сцена: `Assets/EmergencyShift/Scenes/ArtReview/FurnitureLightStudy.unity`.
Откройте её и нажмите Play. Здесь три экземпляра существующей мебели: шкаф `personnel-locker`, стол `lab-workbench` и каталка `transport-stretcher`. Владельцем выбран C, он включается по умолчанию; A/B остаются для сравнения. Исходные PNG, prefab, материалы и прежние сцены не заменяются. Направление принято, массовое подключение остальных материалов ещё не выполнено. Альфа-контуры мебели отдельно исправлены в [проверке форм теней](FURNITURE_SHADOW_SHAPES.md).

## Сравнение в игре

| Управление | Действие |
|---|---|
| 1 / первая кнопка | A: обычный FlatLit, прежнее освещение всей поверхности |
| 2 / вторая кнопка | B: уменьшенная реакция верхней поверхности на фонарь |
| 3 / третья кнопка | C: та же реакция верха плюс матовая кромка, обращённая к источнику |
| WASD / мышь / F | Движение / направление / питание настоящего фонаря |
| Tab | Следующий предмет с переходом на сопоставимую дистанцию |
| V | Следующая из четырёх сторон осмотра |
| L | Потолочный свет: верх мебели освещается независимо от варианта |
| H | Обычные тени фонаря: одинаковое правило во всех трёх вариантах |

Для сравнения сначала выберите предмет и сторону через Tab/V, затем переключайте 1/2/3 без движения. Переход ракурса направляет фонарь на предмет; движение мыши возвращает обычное наведение. Затем обойдите предмет вручную. Проверьте также L с выключенным F: кромка не должна превращаться в собственный светящийся контур.

Кнопки, подсказки, свет и расстановка сохранены в сцене и редактируются в Unity. Авторинг `FurnitureLightStudyBuilder.Create` отказывается перезаписывать существующую комнату. Пункт `Emergency Shift → Art → Build furniture light study` создаёт отдельный Windows development-player в `Builds/FurnitureLightStudy`; он включает экспериментальную сборку через `UNITY_INCLUDE_INSTRUMENTATION`, не меняя обычный список сцен или постоянные scripting defines. Тестовая сцена не добавляется в основной release.

## Как устроена проба

`FurnitureLightStudyProfile` хранит подписи, отклик верхних поверхностей, силу и ширину кромки и дистанцию осмотра. Ссылки на три SpriteRenderer, прямоугольники поверхностей, фонарь и потолочные источники принадлежат сцене. Выбранный вариант и ракурс, блок параметров шейдера и исходные ссылки на материалы принадлежат экземпляру `FurnitureLightStudy2D`. Runtime не меняет общие ресурсы.

У шкафа верх сильнее подавлен, чем у стола и каталки. Это художественные коэффициенты, не метры и не физически рассчитанные высоты. Геометрия поверхности — центр и полуразмеры прямоугольника в локальных единицах SpriteRenderer; исходная оценка берётся из авторского BoxCollider, но далее хранится отдельно и не меняет коллизии. Такой прямоугольник достаточен для пробы трёх крупных форм; сложная мебель потребует более точной маски или нескольких поверхностей.

Шейдер использует реальные URP-текстуры света и их тени. Фонарь и его ближний свет в этой сцене используют существующий blend style 0; слабый фон и потолочные лампы — существующий masked-multiply style 2. Только вклад style 0 получает изменение поверхности. Кромка не добавляет emissive-цвет: без падающего света она не загорается. Каналы 1/3 и normal-mapped lighting этой изолированной пробой не реализуются; этот материал нельзя автоматически назначать остальной библиотеке с произвольной схемой источников.

## Цена и границы теней

Проба меняет получение света поверхностью. Она не создаёт объём, дополнительные ShadowCaster2D или новую физику: отбрасываемые тени остаются обычными плоскими силуэтами URP. Поэтому тень от низкой тележки здесь всё ещё может пересечь столешницу как в прежнем рендере.

B и C в текущей реализации используют один шейдер и одинаковое обновление параметров; кромка переключается коэффициентом. Поэтому упрощение до B само по себе почти не экономит GPU. Контроллер обновляет один переиспользуемый MaterialPropertyBlock для каждого экземпляра, без поиска сцены в Update. Отдельный канал потолочного света означает дополнительную текстуру освещения; при распространении решения на проект это надо учитывать отдельно от стоимости кромки. Индивидуальные блоки параметров и разделение источников также могут ограничить объединение отрисовки.

Возможное следующее развитие:

| Уровень | Работа и стоимость |
|---|---|
| Текущая проба | Измерены три предмета и 60 уменьшенных runtime-копий; существующие тени. Нагрузка полной библиотеки не проверена. |
| Условная высота и проекция на пол | Средняя сложность: один/несколько контуров и высота на предмет, высота источника, отсечение пар по радиусу. Длину тени пересчитывают при движении источника/предмета. |
| Корректные тени на другой мебели | Существенно сложнее: учитывать высоту принимающей поверхности, несколько поверхностей предмета и перекрывающиеся источники. Простого изменения длины напольной тени недостаточно. |
| Полноценные объёмные прокси | Более крупная смена рендера: отдельное согласование 3D-света/теней с текущим 2D Renderer, сортировкой и стилем. Само число полигонов — лишь часть цены. |

У упрощённых коробок геометрия мала; основной риск — число затрагиваемых источников, теневая отрисовка и разрешение буферов, а также подготовка данных на каждый вид мебели. Замер трёх объектов не даёт гарантии FPS для уровня.

Основание для оценки ресурсов URP: [свойства Light2D](https://docs.unity.com/en-us/engine/6000.6/manual/unity2d/2d-urp/2d-index/2d-light-properties-explained) и [объединение 2D-света](https://docs.unity.com/en-us/engine/6000.3/manual/unity2d/2d-urp/2d-index/2d-light-batching-debugger). Реальная цена нового расчёта высот требует отдельной реализации и измерения.

## Измерение 19 октября 2026

[Отчёт и разброс по повторам](../Validation/FurnitureLightBenchmark.json). Windows development-player, Unity 6000.6.5f1, Direct3D11, RTX 3050 Ti Laptop, i7-12650H. VSync выключен, FPS не ограничен. Два последовательных запуска: фактические 1920×1080 и 1920×1200. Запрошенные 3840×2160 были ограничены размером экрана: **4K не проверен**.

На сценарий — шесть перестановок ABC/BCA/CAB/CBA/BAC/ACB; после переключения 0,35 с прогрева и 1,2 с выборки. Перед всем прогоном — отдельный прогрев материалов. Числа ниже — медиана шести медиан сегментов, GPU-время всего кадра, мс. В сцене из трёх предметов камера смотрит на шкаф; плотный сценарий показывает все 60 копий в сетке, масштаб каждой 0,35, и один неподвижный фонарь. Это разные условия, их абсолютные числа нельзя напрямую делить друг на друга.

| Сценарий, потолок выключен | 1080p A / B / C | 1920×1200 A / B / C | Draw calls A / B / C |
|---|---|---|---|
| Три исходных предмета, тени включены | 0,867 / 0,853 / 0,824 | 0,942 / 0,934 / 0,936 | 29 / 29 / 29 |
| 60 копий, тени включены | 4,124 / 4,125 / 4,125 | 4,900 / 4,902 / 4,901 | 321 / 321 / 321 |
| Те же 60 копий, тени выключены | 0,412 / 0,415 / 0,415 | 0,419 / 0,417 / 0,418 | 69 / 69 / 69 |

С потолком и тенями на 60 копиях GPU: 4,235 / 4,237 / 4,237 мс в 1080p и 5,041 / 5,042 / 5,043 мс в 1920×1200; 324 вызова отрисовки во всех вариантах. Выделить стабильный выигрыш B относительно C по этим данным нельзя. Меньшее время A/B/C на трёх предметах местами меняет порядок; это не доказательство ускорения от кромки.

Без теней на 60 копиях парная медиана C−A по времени кадра составила +0,119 мс и +0,133 мс. Разница GPU при этом около нуля: новая работа проявляется преимущественно вне GPU-ограничения. A пропускает обновление параметров, B/C обновляют блоки для 63 записей, включая три скрытых оригинала; этот прототип не отсекает невидимые записи. Парная C−B по кадру нестабильна: +0,056 мс с диапазоном −0,120…+0,214 в первом прогоне, +0,008 мс с диапазоном −0,039…+0,051 во втором. Нельзя объявлять такую разницу гарантированной экономией B.

Счётчик Main Thread включает ожидания и не равен чистой работе CPU; отдельный Render Thread недоступен. GPU-выборки берутся только при новом timestamp FrameTimingManager; пропуски исключаются, не заменяются нулями. Медиана GC-счётчика — 40 байт/кадр во всех режимах вместе с измерителем. Это инструментированная сборка с HUD; числа не являются бюджетом release или обещанием FPS для уровня. Плотная сетка меняет число пересекающихся теней и площадь предметов; она проверяет локальную нагрузку, а не полноценный уровень с врагами и многими фонарями.

Владельцем принят C с прежней системой 2D-теней. Причины переходить на B ради производительности в этих замерах нет. Перед распространением стоит ограничить обновления видимой мебелью; физические высоты и тени между поверхностями остаются отдельной задачей, их цена здесь не измерялась. Приведённые выше цифры измерены до последующего уточнения альфа-контуров; новые данные, если есть, находятся в проверке форм теней по ссылке в начале документа.

Повторение: соберите сцену через указанное меню, запустите видимое окно player с `--furniture-benchmark <absolute-report-json> -screen-fullscreen 0 -screen-width 1920 -screen-height 1080 -force-d3d11`. Каталог отчёта должен существовать. Окно завершится автоматически примерно через 2,5 минуты. Не запускайте параллельно сборки или другие нагрузочные тесты. Сверяйте `width`/`height` в JSON с запросом. Архивы исходных выборок — `Docs/Validation/FurnitureLightBenchmark/*.json.gz`; скрипт `Tools/Environment/summarize_furniture_light.py` пересчитывает статистику.

Проверка интеграции: 86/86 EditMode; Windows build через меню успешен, ошибок/предупреждений 0 в финальной инкрементальной сборке (при первой полной сборке было шесть прежних obsolete-предупреждений в EnvironmentLoadProbe); shader messages 0, missing scripts 0; 310 прежних serialized assets совпали с исходными SHA-256. Сцена после теста чистая, Play остановлен; обычный ManagedCodeVariant и scripting defines восстановлены. Сетка и измеритель в сохранённую сцену не добавляются.
